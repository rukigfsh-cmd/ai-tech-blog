ローカルLLMや画像生成AIを動かしていて「out of memory」「CUDA error: out of memory」と出たり、急に生成が遅くなったりしたら、原因の多くは **VRAM（GPUのメモリ）不足** です。

先に結論を書きます。GPUを買い替える前に、次の順で試すと多くの場合は解決します。

1. **今どれだけ使っているかを確認する**（`nvidia-smi` / `ollama ps` / タスクマネージャー）
2. **ほかのアプリを閉じる**（ブラウザ・ゲーム・別のAIツールもVRAMを使う）
3. **量子化したモデルに替える**（LLMならQ4〜Q5、画像生成ならfp8版など）
4. **コンテキスト長（扱う文章の長さ）を短くする**
5. **KVキャッシュを量子化する**（Ollamaなら `OLLAMA_KV_CACHE_TYPE=q8_0`）
6. **画像生成は解像度とバッチ数を下げ、低VRAM用の起動オプションを使う**
7. それでも足りなければ、**一部をCPU（メインメモリ）に逃がす**か、**小さいモデルを選ぶ**

以下、それぞれの理由とやり方を説明します。

## そもそもVRAMは何に使われているのか

AIの処理でVRAMを使うのは、おもに次の3つです。

| 使い道 | 中身 | 減らし方 |
|---|---|---|
| モデルの重み | モデル本体のデータ。パラメータ数×精度で決まる | 量子化、小さいモデル |
| 作業用のメモリ | LLMならKVキャッシュ、画像生成なら途中の画像データ | コンテキスト長・解像度・バッチ数を下げる |
| ほかのアプリ | Windowsの画面表示、ブラウザ、ゲームなど | 閉じる |

つまり「モデルが大きすぎる」のか「作業用のメモリが膨らんでいる」のかで、効く対策が変わります。

## まず確認：今どれだけ使っているか

**NVIDIA GPU（Windows / Linux）**: コマンドプロンプトやターミナルで次を実行します。

```bash
nvidia-smi
```

`Memory-Usage` の欄に「使用量 / 総量」が出ます。下の表には、どのプロセスがどれだけ使っているかも出ます。

**Windowsのタスクマネージャー**: 「パフォーマンス」タブ → GPU を選ぶと「専用GPUメモリ」の使用量が見られます。「共有GPUメモリ」が増えているときは、VRAMからあふれてメインメモリを使っている状態で、大きく遅くなります。

**Ollama**: 公式FAQのとおり、`ollama ps` でモデルがどこに載っているかが分かります（[Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx)）。

```bash
ollama ps
```

`PROCESSOR` の欄が `100% GPU` なら全部VRAMに載っています。`48%/52% CPU/GPU` のように分かれていたら、入りきらずに一部がCPU側に回っていて、そのぶん遅くなっています。

## 必要なVRAMの見積もり方（LLM）

LLMに必要なVRAMは、ざっくり **「重み」＋「KVキャッシュ」＋「余裕（1GB前後）」** で見積もれます。

- **重み** ≒ パラメータ数 × 1パラメータあたりのビット数 ÷ 8
- **KVキャッシュ** ≒ 2（KとV）× 層数 × KVヘッド数 × ヘッドの次元 × トークン数 × 1要素のバイト数

計算用の小さなPythonスクリプトを置いておきます（このブログの環境で実行して、下の出力を確認しました）。例として、Llama 3.1 8B（32層・KVヘッド8・ヘッド次元128）の数字を入れています。

```python
# ローカルLLMに必要なVRAMのざっくり見積もり（目安）
def weights_gb(params_b, bits_per_weight):
    """モデル本体（重み）のサイズ。params_b は10億単位のパラメータ数"""
    return params_b * 1e9 * bits_per_weight / 8 / 1024**3

def kv_cache_gb(layers, kv_heads, head_dim, ctx, bytes_per_elem=2):
    """KVキャッシュ: K と V の2つ × 層数 × KVヘッド数 × ヘッド次元 × トークン数"""
    return 2 * layers * kv_heads * head_dim * ctx * bytes_per_elem / 1024**3

# 例: Llama 3.1 8B（32層・KVヘッド8・ヘッド次元128）
for bpw, name in [(16, "FP16"), (8.5, "Q8_0"), (4.85, "Q4_K_M(目安)")]:
    print(f"8B {name:12s} 重み {weights_gb(8.03, bpw):5.1f} GB")
for ctx in (4096, 8192, 32768):
    f16 = kv_cache_gb(32, 8, 128, ctx, 2)
    q8 = kv_cache_gb(32, 8, 128, ctx, 1)
    print(f"ctx {ctx:6d}: KVキャッシュ f16 {f16:4.2f} GB / q8_0 約{q8:4.2f} GB")
```

実行結果:

```text
8B FP16         重み  15.0 GB
8B Q8_0         重み   7.9 GB
8B Q4_K_M(目安)   重み   4.5 GB
ctx   4096: KVキャッシュ f16 0.50 GB / q8_0 約0.25 GB
ctx   8192: KVキャッシュ f16 1.00 GB / q8_0 約0.50 GB
ctx  32768: KVキャッシュ f16 4.00 GB / q8_0 約2.00 GB
```

ここから分かることは2つです。

- **量子化の効果がいちばん大きい**: 8Bモデルは、FP16のままだと重みだけで約15GBですが、4ビット前後に量子化すると約4.5GBになり、8GBのGPUにも収まります。
- **長い文章を扱うとKVキャッシュが効いてくる**: 同じモデルでも、コンテキストを4,096から32,768トークンに伸ばすと、KVキャッシュは0.5GBから4GBに増えます。

なお、Q4_K_Mなどの1パラメータあたりのビット数はおおよその値です。実際のファイルサイズはモデルの配布ページで確認してください。層数やKVヘッド数はモデルごとに違うので、Hugging Faceのモデルページにある `config.json`（`num_hidden_layers`、`num_key_value_heads` など）を見て入れ替えます。

## 対策1：量子化モデルに替える（効果：大）

ローカルLLMでは、重みを4〜8ビットに圧縮した **量子化モデル** を使うのが基本です。Ollamaの多くのモデルは、最初から4ビット前後の量子化版が既定になっています。

選び方の目安です（品質の感じ方はモデルや用途で変わります）。

| 量子化 | サイズ（FP16比） | 品質の目安 | 向いている場面 |
|---|---|---|---|
| Q8_0 | 約1/2 | FP16とほぼ同じ | VRAMに余裕がある |
| Q5_K_M | 約1/3 | 差はわずか | 品質重視でVRAMが少し足りない |
| Q4_K_M | 約1/3.3 | 実用上十分なことが多い | 標準的な選択 |
| Q3以下 | さらに小さい | 劣化が目立ちやすい | どうしても入らないとき |

**大きいモデルを強く量子化するか、小さいモデルを軽く量子化するか** で迷ったら、まずは「入る範囲でいちばん大きいモデルのQ4_K_M」から試すのが一般的です。

## 対策2：コンテキスト長を短くする（効果：中〜大）

扱う文章の長さ（コンテキスト長）を伸ばすほど、KVキャッシュが増えます。Ollamaの公式FAQによると、既定のコンテキスト長は4,096トークンで、次の方法で変えられます（[Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx)）。

```bash
# サーバー全体の既定を変える
OLLAMA_CONTEXT_LENGTH=8192 ollama serve

# ollama run の会話中に変える
/set parameter num_ctx 4096
```

長い資料を読ませるために大きな値にしてVRAMがあふれているなら、まず値を下げてみましょう。資料を分割して読ませる、RAG（必要な部分だけを検索して渡す方法）を使う、といった工夫も有効です（[RAG構築入門]({% post_url 2026-10-11-rag-構築-入門 %})）。

また、同じFAQには、同時に処理するリクエスト数（`OLLAMA_NUM_PARALLEL`）を増やすと、必要なメモリが「並列数 × コンテキスト長」に比例して増えると書かれています。個人で使うなら既定の1のままで十分です。

## 対策3：KVキャッシュを量子化する（効果：中）

Ollamaでは、Flash Attentionが有効なとき、KVキャッシュを量子化してメモリを減らせます。公式FAQによると、選べるのは次の3つです。

- `f16`: 既定。精度が高く、メモリも多く使う
- `q8_0`: f16の約半分のメモリ。精度の低下はごくわずかで、多くの場合は気にならない
- `q4_0`: f16の約1/4のメモリ。長いコンテキストでは精度の低下が目立つことがある

```bash
# Linux / macOS のターミナルで試す場合
OLLAMA_FLASH_ATTENTION=1 OLLAMA_KV_CACHE_TYPE=q8_0 ollama serve
```

Windowsでは、システムの環境変数に `OLLAMA_FLASH_ATTENTION` = `1`、`OLLAMA_KV_CACHE_TYPE` = `q8_0` を追加してから、Ollamaを再起動します。この設定はすべてのモデルに効きます。

## 対策4：一部をCPUに逃がす（効果：入るようにはなるが遅い）

どうしてもVRAMに入りきらないとき、Ollamaは自動で一部の層をCPU（メインメモリ）側に置いて動かします。`ollama ps` で `CPU/GPU` と表示されるのがこの状態です。動きはしますが、CPU側の割合が増えるほど遅くなります。

- 「遅くてもいいから大きいモデルを試したい」ときは、そのまま使うのも一つの手です。
- 毎日使うなら、1〜2段小さいモデルか、強めの量子化に替えて **100% GPU** に収めたほうが快適です。

LM Studioでは、モデルを読み込むときの「GPU Offload」の値で、GPUに載せる層の数を手で調整できます（[LM Studioの導入ガイド]({% post_url 2026-08-31-lm-studio-ローカルllm-導入 %})）。

## 画像生成（Stable Diffusion系・ComfyUI）のVRAM不足対策

画像生成では、モデルの重みに加えて「解像度 × バッチ数」に応じた作業用メモリが必要です。

1. **解像度とバッチ数を下げる**: いきなり高解像度で作らず、標準サイズで作ってからアップスケールする。
2. **軽いモデル・fp8版を使う**: 配布元がfp8版や軽量版を用意していれば、それを選ぶ。
3. **ComfyUIの起動オプションを使う**: ComfyUIのソースコード（`comfy/cli_args.py`）には、次のようなVRAM関連のオプションがあります（[ComfyUI cli_args.py](https://github.com/comfyanonymous/ComfyUI/blob/master/comfy/cli_args.py)、2026年11月20日に確認）。

| オプション | 内容 |
|---|---|
| `--lowvram` | 低VRAM向けの動作。最近の版では、動的なVRAM管理が有効なときは何もしない |
| `--novram` | `--lowvram` でも足りないとき |
| `--reserve-vram 1.5` | OSやほかのアプリのために残しておくVRAM（GB）を指定 |
| `--fp8_e4m3fn-unet` | 画像生成モデル本体の重みをfp8で保持してメモリを節約 |
| `--cpu` | すべてCPUで処理（とても遅い） |

```bash
python main.py --reserve-vram 1.5
```

最近のComfyUIはVRAMを自動で管理するので、まずは何も付けずに起動し、エラーが出たときにこれらを試すのがおすすめです。

## ゲームでVRAM不足になる場合

ゲームの場合は、設定の **テクスチャ品質** がVRAM使用量にいちばん効きます。多くのゲームでは、設定画面にVRAMの使用量の目安が表示されるので、それを見ながら「テクスチャ」→「影」→「解像度（またはアップスケーラーの品質）」の順に下げていくと、見た目の劣化を抑えながら減らせます。

## それでも足りないときの選択肢

- **小さいモデルを選ぶ**: 日本語なら、小〜中規模でも日本語が得意なモデルがあります（[Qwen系モデルの日本語性能]({% post_url 2026-09-27-qwen-25-日本語-性能 %})）。
- **GPUを増設・交換する**: ローカルLLMが目的なら、処理速度よりVRAMの容量を優先して選ぶのが定番です。
- **外付けGPU（eGPU）**: ノートPCで使う方法もありますが、接続方式によっては速度が落ちます（[外付けGPUの接続方法]({% post_url 2026-10-13-外付けgpu-egpu-接続 %})）。
- **クラウドを使う**: たまにしか大きなモデルを使わないなら、クラウドのAIサービスやGPUを時間借りするほうが安く済むこともあります。

## よくある質問

**Q. 「共有GPUメモリ」があるのにVRAM不足になるのはなぜ？**
A. 共有GPUメモリはメインメモリを借りている領域で、VRAMよりずっと遅いからです。あふれたぶんがそこに回ると、エラーにならなくても極端に遅くなります。

**Q. VRAM 8GBでローカルLLMは使える？**
A. 7〜8Bクラスのモデルを4ビット前後に量子化すれば、標準的なコンテキスト長で収まることが多いです。上の見積もりスクリプトで、使いたいモデルとコンテキスト長を入れて確かめてください。

**Q. 量子化すると日本語が下手になる？**
A. Q4_K_M程度なら実用上の差は小さいことが多いですが、モデルによって違います。気になる場合は、同じ質問をQ4とQ8で比べてみてください。

## まとめ

- VRAM不足は「モデルの重み」か「作業用メモリ（KVキャッシュ・解像度）」のどちらが原因かを見分ける
- LLMは **量子化 → コンテキスト長 → KVキャッシュの量子化** の順に効く
- 画像生成は **解像度・バッチ数 → 軽いモデル → 起動オプション**
- `ollama ps` で `100% GPU` に収まっているかを確認する
