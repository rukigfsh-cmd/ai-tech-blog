## はじめに：なぜ RAG が必要なのか

大規模言語モデル（LLM）は汎用的な知識を持っていますが、そのデータカットオフの時点で新しい情報にはアクセスできません。さらに、専門的なドメイン知識や企業内部データまで学習するのはコストと計算リソースが膨大になります。

ここで登場するのが RAG（Retrieval-Augmented Generation）技術です。RAG は LLM に検索機能を追加し、外部データから関連情報を取り出し生成に活用するアーキテクチャです。

## RAG アーキテクチャの仕組み

RAG システムは主に 4 つのコンポーネントで構成されます：

1. **ドキュメントインゲスター**：PDF、テキストファイルなどを解析し、セクションごとに分割（チャンキング）
2. **エンベッディングモデル**：各スキャンを数値ベクトルに変換。OpenAI の text-embedding-ada-002 や sentence-transformers が一般的
3. **ベクターデータベース**：変換されたベクトルデータを格納・検索。Pinecone、Weaviate、Milvus など
4. **LLM 生成エンジン**：検索結果をコンテキストとして LLM に渡し、回答を生成

このパイプラインにより、「最新の株価は？」といったクエリでも、学習データのカットオフ日以降の情報を外部ソースから取得できます。

## ステップバイステップでの実装方法

### ステップ1：ドキュメント準備と分割

まず、知識ベースとなるドキュメントを準備します。PDF、Markdown、テキストファイルなどが対象です。

分割戦略が重要で、文単位で分割する（chunk size: 500 tokens）、段落単位、またはセクション単位などがあります。Overlap を設定すると、境界領域の情報が漏れにくいです。

```python
from langchain.text_splitter import CharacterTextSplitter

text_splitter = CharacterTextSplitter(
    separator=".\n",
    is_separator_regex=True,
    chunk_size=500,
    chunk_overlap=50
)
```

### ステップ2：ベクトル化とインデックス作成

分割されたチャンクをエンベッディングモデルで数値化し、ベクター DB に格納します。

```python
from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import Chroma

embedder = OpenAIEmbeddings(model="text-embedding-ada-002")
db = Chroma.from_texts(["ドキュメント1.txt", "ドキュメント2.pdf"], db_folder="rag_db", embedding=embedder)
```

### ステップ3：検索・生成パイプライン構築

LangChain の RetrievalQA チャンネンルが便利です。

```python
from langchain.chains import ConversationalRetrievalChain

question_answering_chain = ConversationalRetrievalChain.from_llm(
    llm=llm_model,
    retriever=db.as_retriever(search_kwargs={"k":5}),
    return_source_documents=True
)
```

このチェーンはユーザーの質問を解析し、ベクター DB から最も関連性の高い 5 ドキュメントを検索し、それらを使用して LLM に回答させます。

## ツールの比較と選定基準

初心者向けには LangChain が推奨です。Python ライブラリで構成されており、学習コストが低く、コミュニティも活発です。

LangChain vs LlamaIndex の比較：
- **LangChain**：汎用性が高い。多数のコンポーネントを組み合わせ可能。ただしコード量が多い
- **LlamaIndex**：RAG に特化。検索戦略（hybrid search、semantic search）が充実。Python API がシンプル

企業用途では Pinecone や Weaviate のようなマネージドベクター DB を採用するのが現実的です。Pinecone は検索速度が速く（ミリ秒級）、日本語の埋め込み精度も高いのが特徴です。

## 実装例：Q&A データベースへの適用

```python
from langchain.chains import LLMChain, ConversationalRetrievalChain
from langchain.llms import OpenAI
from langchain.vectorstores import Chroma

# Q&A ページのデータをインデックス化
qa_data = open("qa_database.txt").read()
db = Chroma.from_texts([qa_data], embedding=OpenAIEmbeddings())

# 検索・回答チェーン構築
chain = ConversationalRetrievalChain.from_llm(
    llm=LLM(model="gpt-3.5-turbo"),
    retriever=db.as_retriever(search_kwargs={"k":2}),
    input_prompt="Based on the following context, answer the question:\n{context}"
)

# 使用例
result = chain.run("Q1: Python の list に要素を追加するメソッドは？")
print(result["answer"])
```

この実装により、数百万件の Q&A データを LLM が瞬時に検索・回答できるようになります。純粋な LLM 生成では「Python のリスト操作メソッド」といった具体的な情報は出力されませんが、RAG なら正確に検索結果から抽出されます。

## 注意点とベストプラクティス

1. **チャンクサイズ**：500-800 tokens が一般的。大きすぎると冗長になる、小さすぎると文脈が欠ける
2. **重複フィルタリング**：検索結果で同一のドキュメントが複数返ってきた場合、上位 1 つだけにするのがコスト削減に効果的
3. **ハイブリッド検索**：キーワードベースとベクトル検索を組み合わせることで精度向上が可能
4. **メトリクス測定**：RAGEval や TruEval のようなベンチマークツールで回答の事実性を定期的に確認

## FAQ（よくある質問）

### Q1: RAG とチャットボットの違いは？
A: チャットボットは固定したスクリプト・フローに基づいて対応しますが、RAG は自然言語クエリに対して動的にデータを検索・生成します。

### Q2: 何のベクター DB を使えばいいですか？
A: 個人開発なら Chroma（LangChain 標準実装）で十分です。本格的な用途では Pinecone が検索速度と日本語対応から推奨されます。Weaviate はスキーマ機能があるため構造化されたデータ管理に適しています。

### Q3: RAG を使えば LLM のハルシネーションは解消される？
A: 完全に解消するわけではありませんが、根拠のある事実情報のみをコンテキストとして提供するため、大幅に改善されます。ただし、検索結果自体の信頼性が問題となる場合もあります（スピアフィッシングなど）。

### Q4: コストを抑える方法はありますか？
A: はい。① 小規模な LLM（GPT-3.5 など）で検索結果を要約させ、GPT-4 で最終回答を生成するハイブリッド方式 ② 検索回数を制限（上位 3 件まで） ③ キャシュ機能を実装

### Q5: Python 以外の言語でも実装できますか？
A: はい。LangChain は JavaScript（LangChain.js）、Java、TypeScript など複数の言語で利用可能です。ただしエコシステムは Python が最も充実しています。
